## Overview & invariants

### The two variants, library-default only
- **AM (Attention Model):** `rl4co.models.zoo.am.AttentionModel` (Kool et al. 2019 REINFORCE). Defaults to use as-is: baseline `"rollout"` (REINFORCE rollout baseline — one epoch of sampling, then the greedy rollout becomes the baseline; promoted each epoch when it beats the current baseline), policy defaults `embed_dim=128, num_encoder_layers=3, num_heads=8, normalization="batch", feedforward_hidden=512`. No `policy_kwargs` overrides.
- **POMO (Kwon et al. 2020):** `rl4co.models.zoo.pomo.POMO`. Defaults to use as-is and **do not override**: `baseline="shared"` (forced — POMO errors on anything else), `num_augment=8` (dihedral8, first augmentation = identity — applied to validation & test only, not train), `num_starts=None` (→ all feasible start nodes at train/val/test; see the cost note below), and its default policy override set (`num_encoder_layers=6`, `normalization="instance"`, `use_graph_context=False` on top of the AM policy).
- **Both variants = the library's default hyperparameters** passed through `RL4COLitModule` (verified defaults, `rl4co/models/rl/common/base.py`): `batch_size=512`, `train_data_size=100_000` (overridable via flags), `val_data_size=10_000`, `test_data_size=10_000`, optimizer **`Adam(lr=1e-4)`** (from `optimizer="Adam"` + `optimizer_kwargs={"lr": 1e-4}`), **`lr_scheduler=None` (no LR scheduler — the real default; do NOT add one)**, `val_batch_size=None` (→ train `batch_size`, 512), metrics `train:["loss","reward"]`, `val/test:["reward"]`. `RL4COTrainer` defaults: `gradient_clip_val=1.0`, `precision="16-mixed"`, `reload_dataloaders_every_n_epochs=1`. The only deliberate non-defaults are the CLI-overridable: data sizes (100k train instances/epoch is overkill for an intro run; the flag keeps it tunable), `max_epochs`, and `max_steps` (Lightning's **total** optimizer-step cap — see the step-counting section). Everything else stays library default.
- **POMO is the expensive variant — plan for it.** POMO trains **multi-start**: `num_starts=None` → `env.get_num_starts(td)` = **all feasible start nodes** (TSP-50: **50**; CVRP-50: **49**, depot cannot start), so every train/validation/test step runs `num_starts` greedy rollouts per instance (batchified into one giant decode: 512 × `num_starts` instances × 50 decode-steps). An AM train step = 2 decodes of 512 × 50 (1 sampling decode for the loss + 1 rollout-baseline greedy decode); a POMO train step = ~50 (TSP-50) / ~49 (CVRP-50) such decodes — **≈25× the decode operations** of AM, plus the 6-layer vs 3-layer encoder — so expect **tens of times the activations/VRAM** per step for POMO at the same batch size, not a fixed constant; a POMO val/test step additionally applies **8 dihedral augmentations** on every instance (i.e. POMO **val** ≈ 8× the POMO train cost). Expect POMO to be the dominant cost of the whole run and the only likely OOM — if it OOMs, the sanctioned fix is lowering `batch-size` (or `--device cpu`) and recording the deviation in `results.md`, never a policy/loss change.
- Training uses the library's own Lightning loop: `RL4COTrainer.fit(model)`. Do not reimplement the train loop, loss, or decode; only wrap it (see orchestrator job list below).

### Problems (env = data generator, fresh instances per epoch)
- **TSP-50:** `TSPEnv(generator=TSPGenerator(num_loc=50))` — `num_loc=50` is **mandatory** (the generator's default is `num_loc=20` for both generators), pass it explicitly; `TSPEnv`'s own default is a 20-city TSP.
- **CVRP-50:** `CVRPEnv(generator=CVRPGenerator(num_loc=50))` — 50 customers + depot, demand = `int(U[0,9](1)) + 1` = **U{1..9}** (10 only at measure zero; not U{1..10}), **capacity 40** (rl4co resolves `CVRPGenerator(num_loc=50)` → `CAPACITIES[50]=40`, the Kool et al. 2019 table; the td `demand` values are pre-normalized to `d/40` by the generator; do not change any of this).
- Data is generated in-memory per epoch (`env.dataset(n, phase=...)`, no `*_file` set) — nothing persisted under `data/`, no disk dependency, resumable by re-derivation from the generator. Train data is re-sampled every epoch (library behavior via `RL4COLitModule.on_train_epoch_end` — keep it, it is the RL4CO training convention); val/test sizes are the flag values; each (variant, problem) run is independent.

### Step counting (Lightning semantics — read before writing the epoch loop)
- A **training epoch** = `ceil(train_data_size / batch_size)` optimizer steps (default 5000/512 ≈ **10 steps/epoch**). Steps/epoch is `ceil(5000/512)`, **not** a fixed 500.
- `RL4COTrainer(max_epochs=E, max_steps=S)` — `max_steps` is Lightning's **total** optimizer-step cap for the whole `fit()` (NOT per-epoch). At defaults S=500 is a safety upper bound that is never reached (10 epochs × ~10 steps ≈ 100 steps < 500); the epoch count `max_epochs` drives the run. Set it as a ceiling to guard against size flags being cranked up. Do not confuse it with per-epoch steps.

### Reward semantics (fixed the plots & results wording)
- Env **reward = negative objective**: TSP reward = −tour length; CVRP reward = −total route length (distance of all routes, depot at index 0). `log_metrics` reports **`train/reward`** and **`train/loss`** during training, **`val/reward`** during validation (no test loop is run; the test-set number in `results.md` comes from a direct manual model call, see the Results section). **Do not read these from `trainer.callback_metrics`** — the hook-ordering pitfall is verified below; capture the per-step floats from the callback's `outputs` instead. The "training return" for each epoch is the **mean of that epoch's per-step `train/reward` values** (see the checkpoint protocol).
- A training return curve is therefore "reward rising toward 0 = getting better". In `results.md` convert to lengths: **length = −reward** (e.g. "AM TSP-50 best-epoch training return −X ± Y ⇒ mean tour length X ± Y").

### Checkpoints — "peak epoch" protocol (per (variant, problem) → 4 files total)
- **Metric:** best epoch-mean **TRAINING return** (mean of that epoch's per-step `train/reward` values, equal-weight mean over the epoch's `ceil(train_data_size/batch_size)` training steps; at defaults ≈ 10 steps/epoch, i.e. ~5 k train instances touched). Higher/less-negative = better. Zero extra inference: every per-step value is already produced by the library's forward pass — the callback just records the floats.
- **Callback (orchestrator-owned, one instance per run):** a Lightning `Callback` with two capture hooks —
  - `on_train_batch_end` → `outputs` is the dict `training_step` returns (`{"loss": <tensor>, "train/loss": <0-d tensor>, "train/reward": <0-d tensor>}`); take `outputs["train/reward"]` (0-d tensor — rl4co 0.7.0 `log_metrics` logs the `.mean()` of the batch reward tensor; the metric is single-mode `on_step`, so the key is exactly `train/reward` — no `_step`/`_epoch` fork). `.item()`, append to the epoch's list.
  - `on_validation_batch_end` → `outputs["val/reward"]` likewise (`.item()`); at the default sizes (val 500 < batch 512) validation is exactly **one batch per epoch**, so the epoch's val return = that single value.
  - **Do NOT read `trainer.callback_metrics` in these hooks — verified off-by-one:** in the installed Lightning the training batch loop fires `on_train_batch_end` hooks *before* `update_train_step_metrics()`, so `callback_metrics["train/reward"]` is still the **previous** batch's value (and stale at epoch boundaries); on the eval side `on_validation_epoch_end` runs *before* `update_eval_epoch_metrics()`. Always take the floats from the hook `outputs`.
  - `on_train_epoch_end` → compute the epoch mean/std over the recorded train rewards, append `(epoch, mean, std, wall_s)` and persist the curve CSV, and **on a new all-epoch best** (epoch 1 always writes; strict improvement thereafter) overwrite-save the checkpoint.
- **Checkpoint file format** (deliberately NOT a Lightning checkpoint): `torch.save({"epoch": <int>, "global_step": <int>, "state_dict": pl_module.state_dict()}, path)` — **state-dict only, no hparams, no optimizer, no lightning extras**, to `src/rl4co_intro/checkpoints/<variant>_<problem>_best.pt`. Overwriting the same file on each new peak keeps **exactly one checkpoint per (variant, problem)** (4 files at defaults: `am_tsp50_best.pt`, `am_cvrp50_best.pt`, `pomo_tsp50_best.pt`, `pomo_cvrp50_best.pt`). Disable the trainer's own checkpointing: `RL4COTrainer(enable_checkpointing=False)` (forwarded to Lightning `Trainer`; otherwise a default `ModelCheckpoint` would fire).
- **Loading** (the recipe in the library is broken here — see API map): build a **fresh** model (`AttentionModel(env)/POMO(env)` with the same env/config as training), call `model.setup(stage="fit")` (creates the baseline child modules so the key sets match) then `model.post_setup_hook()`, then `model.load_state_dict(torch.load(path, weights_only=False)["state_dict"])` **strict** (state-dicts only, the default strict=True). Note the AM (REINFORCE) `baseline` **is** under the `policy` child (a `RolloutBaseline` with its own parameters — a *deep copy* of the actor, the promoted greedy-rollout baseline policy from `on_train_epoch_end`), so those keys **are** in our `state_dict` and load fine under strict; the POMO `SharedBaseline` has no parameters (its "baseline" is just the mean over the multi-start rewards) — the library's own `load_from_checkpoint` has a `load_baseline` path that strips `baseline.*` keys, which only matters if you ever want to reuse it (it doesn't, on this torch — it fails on the pickled hparams before it gets there). Verify the loaded model's eval numbers with a smoke test. The live end-of-training weights are never the reported weights.
- `src/rl4co_intro/checkpoints/` is gitignored (add it to `.gitignore` if missing), mirrors the `src/reinforce_tsp20/checkpoints/` convention.

### rl4co 0.7.0 API map (verified against the installed package — do not guess)
- Imports: `from rl4co.envs import TSPEnv, CVRPEnv`; `from rl4co.envs.routing.tsp.generator import TSPGenerator`; `from rl4co.envs.routing.cvrp.generator import CVRPGenerator`; `from rl4co.models import AttentionModel, POMO`; `from rl4co.utils import RL4COTrainer`.
- `AttentionModel(env)` / `POMO(env)` — env is the first positional arg; all other model args are optional (default kwargs are enough).
- Data API is **model-owned, not env-owned**: `model.setup()` calls `env.dataset(data_cfg[...], phase=...)` with `data_cfg` built from the **model kwargs** (`train_data_size/val_data_size/test_data_size/batch_size/...`). So size control is via **model kwargs**, and nothing needs `generate_default_data` (stays False); the in-memory dataset class is the **env's** `dataset_cls` (default `TensorDictDataset`, set in `RL4COEnvBase.__init__`) — leave it.
- Trainer: `RL4COTrainer(max_epochs=E, max_steps=S, enable_checkpointing=False, num_sanity_val_steps=0, callbacks=[our_callback], **kwargs)` — wraps Lightning `Trainer` (its `__init__` has no named params for these; both `callbacks` and **`**kwargs` are forwarded to Lightning `Trainer.__init__`, so `enable_checkpointing=False` — which disables the default `ModelCheckpoint` — and `num_sanity_val_steps=0` reach Lightning `Trainer`; we checkpoint ourselves). `RL4COTrainer.fit()` is a thin override of `Trainer.fit` (only special-cases `automatic_optimization=False` models) — safe to call normally.
- **What the callback actually reads — hook `outputs`, NOT `callback_metrics`:** in this Lightning install the training batch loop fires `on_train_batch_end` hooks **before** `update_train_step_metrics()`, so inside that hook `trainer.callback_metrics["train/reward"]` is still the **previous** batch's value (and stale/absent at epoch boundaries). On the eval side `on_validation_epoch_end` runs **before** `update_eval_epoch_metrics()`, so `callback_metrics["val/reward"]` is stale there too. Therefore the callback captures the **`outputs`** of the hooks: `on_train_batch_end(trainer, module, outputs, ...)` where `outputs = training_step(...)` = `{"loss": <tensor|None>, "train/loss": <0-d tensor>, "train/reward": <0-d tensor>}`; `on_validation_batch_end(...)` similarly with `outputs["val/reward"]` (0-d tensor). `rl4co 0.7.0` `log_metrics` computes `f"{phase}/{k}"` from `metric_dict` and stores `v.mean() if isinstance(v, torch.Tensor) else v` — hence the 0-d tensors. Take `.item()` per step; epoch mean/std computed in `on_train_epoch_end`.
- **Checkpoint load (the library's `load_from_checkpoint` is broken on this torch):** `REINFORCE.load_from_checkpoint` / `POMO.load_from_checkpoint` → `_load_from_checkpoint` → Lightning `pl_load(..., weights_only=None)`, and on torch 2.11.0 `weights_only=None` defaults to `weights_only=True`, which **cannot** unpickle the checkpoint (REINFORCE/POMO `save_hyperparameters(logger=False)` pickles the full `env`/`policy` into hparams → `_pickle.UnpicklingError: ... Unsupported global: ...TSPEnv`). So our own checkpoints are **state-dict-only** (`{"epoch", "global_step", "state_dict"}`) and we reload with the recipe in the checkpoint protocol (fresh model → `setup(stage="fit")` → `post_setup_hook()` → `load_state_dict(torch.load(path, weights_only=False)["state_dict"])` strict).
- REINFORCE specifics: AM uses the **`"rollout"`** baseline (its default — `RolloutBaseline`): each train step runs the *stored baseline policy* (a deep copy of the actor) on the same batch under `inference_mode` to get the per-instance baseline reward, so an AM train step ≈ 2× a bare rollout (1 sampling rollout for the loss + 1 greedy rollout for the baseline). `REINFORCE.on_train_epoch_end` then runs `baseline.epoch_callback` (a candidate-vs-baseline greedy rollout on the val dataset + one-sided t-test; promotes the baseline policy on improvement) and the train dataset is regenerated — **do not override `on_train_epoch_end`**. POMO uses the **`"shared"`** baseline, which is just `reward.mean(dim=…)` on the multi-start rewards — free, no extra rollouts, no-op epoch callback.
- **What each logged reward means (read before interpreting):** `train/reward` = env reward (−objective) of the **sampling** decode at train. For AM that is 1 tour/instance; for POMO it is the **mean over all `num_starts` greedy tours** (TSP-50: 50, CVRP-50: 49) per instance — same "mean −length" scale, so **AM and POMO `train/reward` are comparable to each other** (POMO's multi-start training is expected to push it higher). `val/reward`/`test/reward` (both `on_epoch=True` means) are for **greedy** decode: POMO takes the **mean over 8 dihedral augmentations × `num_starts` greedy tours** (the `max_aug_reward` is computed but *not* logged; `val/reward` ≈ the 8×num_starts mean), AM is 1 greedy tour/instance. Therefore **train vs val are NOT directly comparable in magnitude** (sampling vs greedy, and POMO is multi-start in both); the plot uses **train** only, and `results.md` states the decode regime exactly as above.

## Mandatory pre-run gate: `nvidia-smi` (before the smoke test AND before the default run)

Another task on this machine is very likely already occupying CUDA — **never assume an empty GPU.** Before *any* run:

1. Run `nvidia-smi`: note which processes hold the GPU, how much VRAM is **free** out of 16 GB, and utilization.
2. Pick device/batch from that:
   - **Smoke test** (tiny: 64 instances, 8 steps) fits in almost any free VRAM; if the GPU is heavily occupied or you can't tell, just run it `--device cpu` — it's seconds, and CPU is a perfectly valid smoke-test device.
   - **Default run**: prefer GPU **only if** the free VRAM has room for the POMO default batch (512 × 50/49 greedy decodes × 50 steps is the single biggest allocation of the whole run). Free VRAM in doubt → lower `--batch-size` (e.g. 256/128 — record the deviation in `results.md`) or `--device cpu`.
   - **CPU full-run rule:** if the estimated CPU wall would exceed **2 h**, do NOT start it — tell the user (free the GPU / wait / shrink sizes) and let the user run it or decide. If you can't confidently estimate below 2 h, treat it as over 2 h.
3. Record the decision (free VRAM at start, occupying processes, device, batch) in the `results.md` Header — it's part of the hardware record.

`--device auto` resolves to cuda whenever `torch.cuda.is_available()`, so an explicit `--device cpu` is required whenever the gate says the GPU is not free.

- [ ] Smoke test (REQUIRED before the default run; must be end-to-end exit 0; device per the nvidia-smi gate — `--device cpu` is always fine, the smoke test is seconds): `python src/rl4co_intro/orchestrator.py --epochs 1 --max-steps 8 --train-data-size 64 --val-data-size 16 --test-data-size 16 --seed 7 [--device <per gate>]` — verifies env construction, model instantiation, the callback's per-step `outputs["train/reward"]` float capture, the checkpoint save/load roundtrip (loaded model reproduces the saved weights — tensor comparison), the single-start greedy eval call (shape `model(td, decode_type="greedy", num_starts=1)`), the CSV curve, and the results.md write. Fix API mismatches here, not during the default run. The 64 < 512 batch means training is 1 step/epoch and `max_steps=8` never binds — both the 1-epoch and full-epoch paths execute once.
- [ ] Default run: `python src/rl4co_intro/orchestrator.py` (defaults: 10 epochs, max_steps=500, train 5000, val 500, test 500, both problems, both variants, seed 42). Record per-(variant, problem) epoch walls from the log.
- [ ] Artifacts present at end (exactly): 4 checkpoint `.pt` files in `src/rl4co_intro/checkpoints/` (gitignored); 4 curve CSVs (`results/rl4co_intro/curves/`) + `results.md` + 2 PNGs in `results/rl4co_intro/`; `results/rl4co_intro/log.txt` with the full run. Nothing else required.
- [ ] Sanity checks to eyeball in results.md before calling it done: epoch-1 train return clearly worse than peak (returns start ~−(cold-start length) and rise toward 0); AM and POMO both present on both problems; POMO curves generally higher (less negative) than AM's at equal epochs (expected, multi-start training advantage — if it is NOT the case, do not panic, just report what was measured); lengths are in a sane range (rewards are raw [0,1] distances: TSP-50 near-optimal ≈ 4.0 (0.5649·√n), unmeasured NN ≈ 5.6–7.0, untrained-policy greedy ≈ 15–16, random permutation ≈ 25 — a sane *trained* length is between the NN range and slightly past it; if a column shows ~15+ or ~25, the checkpoint load or eval path is broken, not the model; CVRP-50 total route length: NN ≈ 14.8–16.5, a sane trained value is at/below NN on the same instances).
- [ ] Commit is the user's (do not `git commit`).
